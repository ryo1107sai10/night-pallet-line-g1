# Night PRO LINE

要件定義書 第1.0版に基づくLINE接続・シナリオ・顧客台帳・来店予約の実装です。管理画面とAPI、PostgreSQLのマイグレーション、LINE配信ワーカー、ローカル試験を含みます。

## ローカルで起動

Node.js 24以上とnpmが必要です。ローカル起動はnpmに組み込みPostgreSQLのバイナリがある環境（例としてmacOS arm64）に対応しています。展開したフォルダで以下を実行します。

```sh
npm ci
npm run build
npm run local
```

1. ブラウザで [管理画面](http://127.0.0.1:3000/master/) を開きます。
2. 初回起動で作成される `.local/first-invite.json` を開きます。認証アプリに `setup_key` を時刻ベースで登録し、管理画面の「招待を受け取った方」に `invite_code`、新しいパスワード、現在の6桁コードを入力します。
3. 法人ID `demo`、メール `admin@example.test`、設定したパスワードと**次の6桁コード**でログインします。
4. 「新しい店舗を登録」から店舗を作り、「LINE接続」から公式アカウントの設定を登録できます。

初回招待は24時間有効です。有効化前に期限切れになった場合は、起動中のアプリを停止し `npm run local -- --renew-invite` で再発行します。ポートが使用中の場合は、`LOCAL_WEB_PORT` と `LOCAL_DB_PORT` を変更できます。ローカルデータは `.local/` に保存されます。初回招待を利用した後は、`.local/first-invite.json` を削除できます。

ローカル起動では実LINEへの検証・送信を無効にしています。ローカル結合試験ではLINE API応答を差し替え、HTTP、実PostgreSQL、ワーカーを通して確認します。

```sh
npm test
```

公開URLの `/` は予約の入口です。公開済みの予約をトップに表示するときは、その接続IDを `PUBLIC_BOOKING_CONNECTION` に指定します。マスターは `/master/` からログインします。

既存の法人では、新しいアプリを公開する前に移行用DBロールで `npm run setup -- --master <法人ID> <既存の有効な法人管理者メール>` を実行します。新規法人には、初回招待を発行した法人管理者が指定されます。マスターを変更すると、前の法人管理者のセッションを取り消します。

## 管理会社と契約店舗の運用

リルコーポレーションの北村さんは `/platform/` からエールを監督します。エールは `/master/` から契約店舗を切り替え、店舗ごとにステップ配信を作成・編集・運用します。`/staff/` はエールから招待を受けたスタッフ用です。移行前の非マスターアカウントは既定で利用を停止します。

北村さんの初回招待は、移行用DBロールで発行します。出力は本人へ安全に渡し、`/platform/` の「招待を受け取った方」で有効化します。

```sh
(umask 077 && npm run --silent setup -- --invite-supervisor <エールの法人ID> lilu リルコーポレーション 北村さん <本人のメールアドレス> > supervisor-invite.json)
```

### 登録フロー（法人の新規登録と店舗のセットアップ）

新しい契約法人の登録は、北村さんが `/platform/` の「新規登録」から行います。法人名・店舗名・エール担当者のメールアドレスを入力すると、法人と最初の店舗の作成、担当者への招待（その法人のマスターになります）、初期設定テンプレートの適用までを一括で実行し、法人ID・招待コード・設定キー・ログイン画面のURLを表示します。初期設定テンプレートは、店舗機能の基本4機能（顧客タグ・来店予約・面談予約・Googleカレンダー照合）が有効で追加機能は無効、面談受付時間は18:00〜24:00、タイムゾーンは Asia/Tokyo、営業日の締め時刻は06:00です。店舗の所在地・営業区分・責任者は仮の「未設定」で作成され、エール側のセットアップで入力します。

`/platform/` の「登録の進捗」では、監督中の管理会社とウィザードで作成した法人について、店舗ごとに「招待の有効化待ち」「LINE接続の状況」「セットアップの確定数」を確認できます。承認のための画面ではなく、どこで止まっているかを見て支援するための一覧です。各法人の行では、有効な法人管理者のメールアドレスを指定してマスターに切り替えることもできます（従来の `npm run setup -- --master` と同じ操作の画面版で、CLIも併存します）。

招待を受け取ったエール担当者は `/master/` にログインし、店舗ごとに「店舗セットアップ」を進めます。ステップは、1. 店舗情報、2. 使う機能、3. 面談の受付時間、4. LINE接続、の4つです。各ステップは、内容を自分で決めて保存し「確定」する形式で、重要な設定を既定値のまま自動で決めることはしません（各機能には説明と、後から変更できる旨を表示します）。確定した後にその設定を変更すると、そのステップだけ未確定に戻り、再確定が必要になります。進み具合は自動で保存されるため、途中まで決めて後から再開できます。管理会社（北村さん）の承認は不要で、4ステップすべてが確定するとセットアップを完了できます。LINE接続のステップでは、自動で判定できる項目（トークン照合・Webhook疎通・テスター本人確認・受信・送信受付）は自動表示し、公式管理画面でしか分からない項目はLINE接続パネルの確認チェックで「自分で確認した」として保存します。

店長は店舗のLINE公式アカウントアプリでチャットに返信します。LINE側の「応答設定」でチャットをオンにし、「権限管理」で店長にチャットの権限を付与します。Night PRO LINE側では、エールが「店舗業務・LINE受信箱」で会話を開き、「店長へ引き継ぐ」を押します。その会話へのNight PRO LINEのステップ配信、絞り込み配信、予約通知とアプリからの返信を一時停止します。停止中に処理された配信は見送り、設定時刻または「店長対応を終了する」で以降の自動対応を再開します。LINE公式アカウント側で別途設定された自動応答はLINE側で管理します。

## 実LINEでG1を検収

検証担当者が管理できるテスト用LINE公式アカウントと公開HTTPS環境を用意します。実際に利用する店舗、アカウント所有権とプロバイダー、LINEの利用条件は D01〜D04・D14 の記録に従って確定します。

1. PostgreSQLに移行用ロールと実行用ロールを作ります。移行用は対象DBでスキーマ作成・所有ができる構成とし、実行用は `LOGIN NOSUPERUSER NOBYPASSRLS` とし、所有者ロールのメンバーにしません。初回設定で `.env.example` を参照して `PUBLIC_ORIGIN`、`MASTER_KEY`、`DATABASE_URL`、`MIGRATION_DATABASE_URL` を設定します。
2. ビルド後に `npm run setup -- pilot "検証用法人" admin@example.test` を実行し、表示された招待を管理者に渡します。マイグレーションのみ実行する場合は `npm run setup` です。サーバー・ワーカーには実行用のDB接続情報と暗号鍵を設定し、移行用の接続情報は初回設定時だけ使用します。
3. `npm start` と `npm run worker` を起動します。既定ではアプリは `127.0.0.1:3000` で待ち受けます。HTTPSの入口から転送し、公開URLは `PUBLIC_ORIGIN` と一致させます。プロキシ配下のIP制限は接続元単位で機能するよう入口にも設定してください。
4. 管理画面で店舗と検証用OAを登録します。プロバイダー、OA所有、各チャネルID、ボットユーザーIDをLINE Developersで照合し、認証情報は管理画面の専用欄に入力します。
5. 接続画面に表示されたURLをLINE Developersに設定します。Webhookを有効にして再送を設定し、既存の応答設定・ツールとの重複を点検します。LINEログインチャネルを公開し、LIFFのスコープに `openid` を追加します。LIFFのエンドポイントは表示されたURLをそのまま登録します。
6. 管理画面で公式管理画面の確認結果を保存し、「トークンとボットの照合」「Webhookの疎通」の順に確認します。公開中のOAのWebhookを変更する場合、既存ツールに影響するため、ここでは検証用OAを使用します。
7. 開発者権限のないテスト利用者へLIFF URLと用途付きの招待コードを渡します。本人確認とテストメッセージの受信許可を行ってもらい、同じLINEアカウントから検証用OAへメッセージを送ってもらいます。「テストの進捗を更新」で受信を確認し、テスト送信を1通だけキューに登録します。
8. 管理画面の「LINE受付済」と実機の受信を照合し、公式管理画面の確認欄に実機確認を記録します。「接続済」は全項目の確認後に表示されます。試験日、使用したOA、端末、操作担当、結果を記録します。

この構成はG1の接続検証用です。本番運用に向けて、D10〜D12の保存・鍵管理・監視・復元体制、認証回復と運用者委任、利用規模に応じたワーカー分割と負荷試験を確定します。

## 顧客・予約と自動配信

「顧客・予約」管理画面から、顧客台帳、来店受付枠、予約確定・変更・取消、配信結果を参照できます。顧客はLINE内画面で用途別の受信設定、来店申込、本人の予約変更・取消を操作できます。

公開版の自動実行は `AUTO_SEND_ENABLED`、店舗の有効化、契約と適格性、LINE接続確認、用途別の同意に従います。実機検収に必要な設定と、現在対象にしているイベントは [実LINE検収手順](LIVE-LINE.md) を参照してください。

### 店舗ごとの機能設定と顧客タグ

- 法人管理者が「操作する店舗 → 店舗で使う機能」で、顧客タグ・来店予約・面談予約・Googleカレンダー照合を個別に切り替えます。自動配信は「顧客・予約 → 自動配信」で設定します。「面談枠の管理」「顧客・予約」を開くと選択中の店舗を引き継ぎます。
- 来店予約と面談予約を停止しても、利用者は既存予約の確認・取消ができます。Google照合だけを停止した場合、既存の連携設定は保存され、店内の予約と受付停止時間で空き枠を判定します。
- 「顧客・予約 → 顧客タグ」でタグを作成し、友だち追加（顧客専用の公式アカウント）、来店予約の確定、来店記録のいずれかで自動付与する条件を設定できます。顧客台帳から手動の付与・解除、全タグ一致／いずれか一致の絞り込み、条件の保存・呼び出しができます。シナリオでもタグの付与・解除・保有判定ができます。
- 顧客タグを停止した店舗では、手動・自動のタグ更新、タグによる絞り込み、タグを使う自動シナリオが停止します。タグや保存した絞り込みは保持します。これらのタグは顧客台帳で利用し、採用データとは分離しています。

更新時は `npm run setup` で `007_store_features.sql` を適用してからアプリとワーカーを切り替えます。既存の店舗機能は有効で開始し、従来の自動配信の設定を引き継ぎます。[プロラインの管理画面](https://autosns.co.jp/manual/start/connect/main_menu) · [Lステップのタグ機能](https://linestep.jp/lp/01/features22.html)

## 採用面談の予約

採用用または兼用のLINE公式アカウントとLIFFを登録したら、管理メニューの「面談枠の管理」から対面面談の日時、所要時間、会場案内を設定します。法人管理者・店舗責任者・採用担当が担当店舗の枠を公開できます。公開枠は1枠1名で、同じ店舗の公開・確定枠の時刻は重複できません。公開停止後も、すでに確定した予約は維持されます。

応募者はLINE内で本人確認し、週間カレンダーから対面面談の日時を選び、確認画面で予約を確定します。日程変更と取消は「自分の面談」から行えます。面談予約は来店予約と別の台帳で管理されます。初めて面談予約を導入する既存環境では `npm run setup` で `004_interviews.sql` などのマイグレーションを適用します。

[面談予約の公開デモ](https://ryo1107sai10.github.io/night-pallet-line-demo/interview/) では架空の枠で予約・変更・取消を試せます。実際のLINE公式アカウントでの検収は未実施です。

公開HTTPS環境への配置、店舗ごとのLINE・Google接続、実機での重複確認は [採用面談の実機検収手順](LIVE-INTERVIEW.md) を参照してください。

面談カレンダーは店舗の現地時刻で、既定は **18:00〜24:00、30分刻み**です。最終開始は30分面談の場合の23:30です。「面談枠の管理 → 受付時間の設定」で開始・終了を変更できます。受付時間は表示・予約可能な範囲で、予約を受け付けるには管理者が範囲内の枠を公開します。時間外になった枠は新規受付から外れ、確定済みの面談は「自分の面談」から確認・変更・取消できます。更新時は `npm run setup` で `005_interview_hours.sql` を適用してください。

### LIFFなし面談予約（トークンリンク）

採用専用の公式アカウントでは、LIFFを使わずにLINEトークから面談予約へ進む導線も使えます。店舗の機能設定で「LINEトークからの面談予約（LIFFなし）」を有効にし、`npm run setup` で `022_interview_link_tokens.sql` を適用してからアプリとワーカーを再起動します。

1. LINE公式アカウントマネージャー（またはMessaging API）で、共通リッチメニューの「面談を予約する」ボタンを **postbackアクション** に設定し、データに `action=interview_link` を入れます。ユーザーごとの個別メニューは不要です。
2. 応募者がボタンをタップすると、Webhookのpostbackを受けてサーバーが推測不可能なトークン付きURL（`https://{公開オリジン}/reserve/{接続ID}?t={トークン}`）を発行し、Pushメッセージで送ります。有効期限は発行から3時間で、再タップすると古いリンクは無効になります。
3. 応募者はURLをそのままブラウザで開き（LIFFの認証画面は出ません）、既存の面談カレンダーから予約します。本人の紐づけはLIFF経路と同一のため、採用ケース・確定通知・リマインド・リッチメニュー切替はそのまま連動します。予約が確定すると、そのリンクは使用済みになります。
4. 確定通知には、予約の確認・変更・取消に使う新しいリンクが同梱されます。期限切れ・使用済みのリンクを開いた場合は、メニューの再タップを案内する画面が表示されます。

フェーズ1の対象は採用専用OAのみでしたが、フェーズ4で兼用OAの postback からも発行できるようになりました（下記「兼用OAと顧客リンクのシナリオ差し込み」参照）。LIFF経路も従来どおり併用できます。実機での検収手順は [実LINE検収手順](LIVE-LINE.md) の「LIFFなし面談予約の検収」を参照してください。

#### ステップ配信（シナリオ）からの面談予約URL（フェーズ2）

採用シナリオのメッセージ本文では、差し込み項目「面談予約 URL」（`{{interview_link}}`）が使えます。シナリオ編集画面の差し込みボタンと、配信前テストのシミュレーション値入力に自動で表示されます（シミュレーションでは任意の https URL をダミー値として入れます）。顧客向けシナリオでは使えません（検証エラーになります）。

実際の送信では、ダミー値や固定URLは送られません。送信の直前に、受信者ごとにトークンを発行してその人専用のURLへ差し替えます。発行の条件はリッチメニューの postback と共通で、採用専用OA・友だち状態・「面談予約」と「LINEトークからの面談予約（LIFFなし）」の両機能が有効・店舗と法人が停止中でないこと、をすべて満たす場合のみです。条件を満たさない受信者にはURLを送らず、その送信自体を取りやめます。再発行のたびに古い未使用リンクは無効になるため、有効なリンクは常に1人1本です。トークンの有効期限（3時間）は送信時点から数えます。

現在の配信経路のうち、この差し替えが働くのはシナリオの「配信前テスト」送信です。採用シナリオの実配信（自動配信エンジン）は現行では顧客向け用途のみが対象のため、採用のステップ配信を実配信する場合は、その配信処理から送信直前の差し替えを呼び出す組み込みが別途必要です。

#### LIFFなし全機能化（フェーズ3）

`npm run setup` で `023_liff_free_links.sql` を適用すると、LIFFなしでも接続・運用が完結するようになります。LIFFを設定済みのチャネルは従来どおり動き、LIFF経路は併存します。

- **接続登録と検収**: チャネル登録で LINEログイン チャネルIDと LIFF ID は任意になりました。空欄で登録すると Messaging API だけの接続になり、検収（接続済み判定）でも LINEログインの公開確認と LIFF 本人確認は求めません。LIFF を設定したチャネルでは、従来どおり両方が揃うまで「接続済み」になりません。
- **テスター本人確認（メッセージ方式）**: テストコードの確認は、LIFF画面での入力に加えて、公式アカウントのトークで「接続テスト {テストコード}」と送信する方法でも行えます（従来はモジュール経路のみ）。LIFFなしチャネルでは管理画面の招待表示がこの方式の案内になります。確認後にもう1通メッセージを送ると受信の証跡が立ち、テスト送信へ進めます。
- **顧客向けトークンリンク**: 顧客専用の公式アカウントでも、リッチメニューの postback（データ `action=customer_link`）から本人専用URL（`https://{公開オリジン}/account/{接続ID}?t={トークン}`）を Push で送れます。店舗の機能設定で「LINEトークからの来店予約・設定（LIFFなし）」を有効にしてください。URLを開くと LIFF の認証画面なしで本人確認が成立し、LIFF版と同じ来店予約・配信設定・回答フォームが使えます。トークンの有効期限は3時間、セッションは2時間です。基盤は用途非依存の `link_token` テーブル（`src/link-token.ts`）で、面談は従来の `interview_link_token` のままです。
- **流入分析の移行**: 流入元は LIFF のないチャネルでも作成できます。postback データに `source={流入元ID}` を付けると（例: `action=interview_link&source={流入元ID}`）、発行されるトークンに流入元が紐づき、引換（本人確認）の時点で帰属が記録されます。流入元の一覧では、LIFF のあるチャネルは従来どおり LIFF URL、ないチャネルは postback データの文字列を表示します。QRコードは従来どおり LIFF 前提です。

フェーズ3の対象は専用OA（採用・顧客）でした。兼用OAの postback 発行と顧客リンクのシナリオ差し込みはフェーズ4で実装しました（下記）。実機での検収手順は [実LINE検収手順](LIVE-LINE.md) の「LIFFなし接続・顧客リンクの検収」を参照してください。

#### 兼用OAと顧客リンクのシナリオ差し込み（フェーズ4前半）

- **兼用OAでの postback 発行**: 顧客・採用兼用の公式アカウントでも、リッチメニューの postback から面談リンクと顧客リンクの両方を発行できます。用途の振り分けは postback データの `action` が担います（`action=interview_link` は面談、`action=customer_link` は来店予約・設定）。間違った用途の引換はできません。発行条件（友だち状態・各機能フラグ・店舗と法人の停止状態）は専用OAと同じです。流入元の `source={流入元ID}` も兼用OAで使えます。なお、採用シナリオのテスト送信に含めた面談予約URLの差し替えは、従来どおり採用専用OAのみが対象です（兼用OAでは送信を取りやめます）。
- **顧客リンクのシナリオ差し込み `{{customer_link}}`**: 顧客シナリオのメッセージ本文で、差し込み項目「来店予約・設定 URL」（`{{customer_link}}`）が使えます。シナリオ編集画面の差し込みボタンとシミュレーション値入力に自動で表示されます。採用シナリオでは使えません（検証エラーになります）。実際の送信ではダミー値や固定URLは送られず、送信の直前に受信者ごとにトークンを発行して専用URLへ差し替えます。テスト送信と実配信（自動配信エンジン）の両方で差し替えます。発行条件を満たさない受信者にはURLを送りません（テスト送信は取りやめ、実配信はそのメッセージを保留します）。再発行のたびに古い未使用リンクは無効になるため、有効なリンクは常に1人1本です。トークンの有効期限（3時間）は送信時点から数えます。店舗の機能設定で「LINEトークからの来店予約・設定（LIFFなし）」が有効なことが条件で、兼用OAに紐づけた顧客シナリオでも使えます。

実機での検収手順は [実LINE検収手順](LIVE-LINE.md) の「兼用OA・顧客リンクのシナリオ差し込みの検収」を参照してください。

### Googleカレンダー連携と面談の受付停止

管理画面の「面談枠の管理」で、店舗ごとにGoogleカレンダーを1件連携できます。公開済みの面談枠のうち、Googleで予定ありとされる時間、確定済みの面談、管理画面で設定した受付停止時間に重なる枠を受付不可にします。新規確定と日程変更の直前には最新の状態を再確認します。Googleから空きを確認できない場合は対象店舗で新規確定・日程変更を保留します。確定済みの面談の確認と取消は利用できます。

休日や休憩などは「面談を受け付けない時間」の開始・終了を入力します。停止時間に確定済みの面談が重なる場合は管理者に件数を表示し、予約自体は維持します。

1. Google CloudでGoogle Calendar APIを有効にし、OAuth同意画面とウェブアプリケーション用のOAuthクライアントを設定します。テスト中の外部アプリでは利用するGoogleアカウントをテストユーザーに追加します。
2. 許可するリダイレクトURIは、公開HTTPSのオリジンに `/interview/google-return.html` を付けたURLです。サーバーに `GOOGLE_CALENDAR_CLIENT_ID` と `GOOGLE_CALENDAR_CLIENT_SECRET` を設定し、`npm run setup` で `006_interview_availability.sql` を適用します。
3. 「面談枠の管理 → Googleカレンダー連携」で `primary` または共有カレンダーのIDを入力し、Googleの権限確認を完了します。共有カレンダーは連携するGoogleアカウントに空き状況の参照権限が必要です。

Googleとの連携は既定で空き状況を参照します。オプションの予定登録は下記を参照してください。確定直前の照合より後でGoogleに追加・変更された予定は、管理画面で調整します。アプリから連携を解除するとアプリ内の接続情報を消去し、Googleの許可はGoogleアカウント側でも取り消せます。リバースプロキシのアクセスログにはOAuthコールバックのクエリ文字列を記録しないでください。実際のGoogleアカウントでの接続確認は公開HTTPS環境で実施します。

[Google Calendar FreeBusy API](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query) · [Google OAuth設定](https://developers.google.com/identity/protocols/oauth2/web-server)

## 店舗業務

法人管理者が「店舗で使う機能」で必要な機能を店舗単位でオンにします。追加機能の初期値はオフです。「店舗業務」で顧客用と採用用を選びます。既存環境は最新の `npm run setup` を実行し、アプリ・ワーカーを同時に切り替えます。

| 画面・機能 | 使い方 |
| --- | --- |
| 回答フォーム | 公式LINEと用途ごとにフォームを作成し、短文・長文・選択肢・チェック欄を設定できます。公開リンクはLINE内で本人確認を行います。回答は質問と題名の版を保存します。採用フォームで応募者名の項目を指定できます。 |
| 応募・選考 | 採用フォームへの回答または面談予約で応募者を登録し、面談実施・体入予定・体入実施・入店・辞退を記録します。 |
| 流入分析 | 店舗・公式LINE・用途別の経路リンクとPNGのQRコードを発行します。最初に有効な経路から本人確認を終えた人を集計し、回答・予約・面談実施・体入実施・入店を追います。 |
| 絞り込み配信 | 保存したタグ条件や最終来店日から対象を選び、人数・除外理由・本文を確認して承認します。送信時も販促同意、年齢確認、ブロック、有人対応、頻度、通数を再確認します。日付をまたぐ送信時間を指定できます。 |
| リッチメニュー | 同じ公式LINEのMessaging APIで用意した通常時と予約確定時のリッチメニューIDを登録します。兼用アカウントでは最後に認証した用途を採用します。 |
| LINE受信箱 | 1対1のトーク本文、担当者、対応状態、内部メモ、テキスト返信とLINE受付結果を扱います。兼用の受信は受付保留から担当者が用途を確認します。送信取消済みの本文は表示から取り除きます。 |
| 面談のお知らせ | 応募者がLINE内で通知を許可すると、確定案内と前日18時のリマインドを予約します。直前の申込みでは確定案内のみです。キャンセル待ちでは枠が空いた際に先着の希望者1名へ案内します。 |

| 運用チェック | 未公開フォーム、LINEの接続検収待ち、用途未分類の受信、送信結果不明、Googleへの反映失敗を表示します。 |

Googleへの予定登録を使う店舗は「Googleカレンダーへの面談登録」をオンにし、Google連携をやり直して予定の編集権限を許可します。接続するGoogleアカウントには担当者の共有カレンダーを参照・編集できる権限が必要です。面談の作成・変更・取消はワーカーが処理し、Googleの件名に応募者名を含めません。書き込み停止中はGoogleに既に作成された予定が残ります。Googleアカウントを切り替える場合は旧カレンダーの予定も確認します。
